# Release notes

## Release identity

Record the verified API/documentation version, environment, and publication/rollout dates. Mark draft dates unresolved until confirmed.

## New capabilities

For each change, state the business benefit, affected operations, response or input differences, and links.

## Action required

Explain consumer changes, compatibility risks, deadlines, and migration guidance. Review enum additions and tightened constraints carefully.

## Deprecated and removed

Distinguish warnings from actual removal. Name the replacement and semantic differences.

## Fixes and known limitations

Describe observable behavior, not internal implementation chatter. State remaining limitations honestly.

## Evidence and approval

Link updated contracts, examples, tests, and review decisions before publication.
